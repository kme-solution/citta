# Cetasika (စေတသိက်) — digital model

**State:** researched design specification; this file does not certify implementation. Read [Myanmar explanation](01-buddhist-explanation.md) before this document and [implementation design](03-implementation.md) afterward. Actual delivery evidence belongs to [status](../../../delivery/status.md).

## Purpose and interpretation

Cetasika owns doctrinal factor catalog and association rules for reference. Runtime modeled facets must each have their own contract; catalog presence must never be reported as implemented feeling, attention or wisdom.

The source identifiers CS-S1 onward belong to document 01. The requirements below are original engineering choices informed by that research, not statements attributed to the Buddha. Source-layer and terminology limits in document 01 apply. No database field, model response or software timing establishes a literal mental factor.

## Behavioral requirements

### CS-01 — Source-backed rules

Each association rule needs a source locator and explicit applicability, including conditional mutual exclusions. Type-ID spelling must not be its only documentation.

### CS-02 — Classification versus occurrence

A factor permitted for a reference citta is not evidence it actually occurred in an agent decision.

### CS-03 — Projection correctness

89/121 parent-child mappings must preserve associations and expose distinct detailed cases rather than flatten conditional differences.

### CS-04 — Unknown and review status

Unknown IDs fail explicitly; unresolved doctrine/translation remains pending, not filled by model guesses.

### CS-05 — Runtime separation

Keep reference associations separate from modeled appraisal, authority and executable behavior. No automatic creation of 52 agent microservices.

## Cooperation and ownership

Citta-sangaha supplies type IDs; cetasika supplies associations; citta-vithi uses them for simulation; vedana/manasikara/cetana implement separately limited software facets.
