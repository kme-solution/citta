# Nivarana (နီဝရဏ) — coding and implementation design

**State:** documentation and read-only source assessment; proposed changes are not implemented by this file. Behavioral authority is the [digital model](02-digital-model.md); research belongs to the [Myanmar explanation](01-buddhist-explanation.md). Application execution requires the existing explicit-authorization gate.

## Current code and gap

Current focus history, unchanged-turn eligibility, progress summaries and modeled tendencies contain possible inputs, but no dedicated pattern-evidence/review contract exists. A repeated string or timeout alone is not a sufficient classification.

## Proposed record and interfaces

Propose PatternReview with concern ID, observed sequence refs, narrow behavioral description, counterexplanations, uncertainty and bounded recommendation. Use engineering pattern names in runtime records; map doctrinal inspiration only in reference metadata. Initially embed review in paccavekkhana/viriya policy; a separate `nivarana/` source module is justified only if shared logic warrants it.

## Integration and state transitions

Review committed history and actual outcomes, not inaccessible provider thoughts. Supply a qualified recommendation to effort/concern reconsideration. Cetana adopts any changed direction under current evidence/authority. Shared citta stores the review reference; no second monitoring agent autonomously redirects the foreground.

## Failure, recovery and compatibility

Insufficient history means unassessed. Provider/slowness failures are operational causes until evidence supports another description. Preserve prior records and alternative explanations; an erroneous pattern assessment can be corrected. No mood, suffering or attainment status is backfilled.

## Delivery slices and verification gates

1. Define narrow observable patterns and counterexplanations before detectors.
2. Integrate as a bounded review/effort facet; avoid a separate service or speculative psychology engine.
3. Verify true and false positives, legitimate uncertainty and correction/recovery under actual histories.

Acceptance is defined by NI-01 onward and the NI-C scenarios in document 02. When execution is authorized, start with meaningful focused checks, then isolated persistence/integration checks where needed, then actual provider/portal observation for semantic behavior. Catalog-only checks should inspect authoritative data and representative classifications. Never claim a runtime outcome from this source review.

No application source, dependency, migration or running service is changed by this documentation. Keep historical records, private configuration and applied migration checksums intact. Proposed API/schema changes require explicit compatibility and version handling in their implementation slice. Actual completion, limitations and the next safe task remain in the existing delivery status document.
