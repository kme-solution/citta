# Khandha (ခန္ဓာ) — digital model

**State:** researched design specification; this file does not certify implementation. Read [Myanmar explanation](01-buddhist-explanation.md) before this document and [implementation design](03-implementation.md) afterward. Actual delivery evidence belongs to [status](../../../delivery/status.md).

## Purpose and interpretation

Khandha is a reference/explanatory projection for the doctrinal learning surface. It must not become five runtime workers or relabel CPU, database and provider output as human aggregates.

The source identifiers KH-S1 onward belong to document 01. The requirements below are original engineering choices informed by that research, not statements attributed to the Buddha. Source-layer and terminology limits in document 01 apply. No database field, model response or software timing establishes a literal mental factor.

## Behavioral requirements

### KH-01 — Reference boundary

Return doctrinal explanation for the selected catalog/simulator context, not a live diagnosis of Kyaw2.

### KH-02 — No false identity

Do not call hardware rupa-khandha or model text vinnana as established fact.

### KH-03 — Contextual labeling

Make simulation assumptions, source layer and unavailable detail visible. Generic descriptions cannot stand for independently modeled facets.

### KH-04 — Stable linkage

Reference actual catalog/process IDs and keep mappings versioned; do not infer unseen mental states from task success.

### KH-05 — Separate product views

Mind/Memory/Activity show actual software records. Khandha reference belongs in Catalog/learning views with clear boundaries.

## Cooperation and ownership

Khandha is a reference projection; citta-vithi is a simulator; cetasika/citta-sangaha supply classifications. Application modules retain their actual operational responsibilities and do not form five literal aggregates.
