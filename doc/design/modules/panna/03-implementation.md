# Panna (ပညာ) — coding and implementation design

**State:** documentation and read-only source assessment; proposed changes are not implemented by this file. Behavioral authority is the [digital model](02-digital-model.md); research belongs to the [Myanmar explanation](01-buddhist-explanation.md). Application execution requires the existing explicit-authorization gate.

## Current code and gap

Proposal checks validate evidence IDs/criterion strings, while outcome review normalizes operations and the provider supplies most semantic judgments. There is no explicit, attributable support/assumption/consequence assessment shared before adoption and after feedback.

## Proposed record and interfaces

Propose DiscernmentAssessment with object/inquiry IDs, material claim-support links, assumptions, counterevidence, conclusion limits and expected consequence uncertainty. Separate provider-assessed semantic content from independently verified source/reference checks. A `panna/` pure contract/policy module can consume these; no ungrounded wisdom score or autonomous judge service is introduced.

## Integration and state transitions

Consume examination and retained evidence; return a bounded assessment to resolution/cetana and independent sikkha checks. After actual feedback, paccavekkhana compares predictions with outcomes and sati may retain attributable findings. No silent policy rewriting or source-status promotion follows from a positive assessment.

## Failure, recovery and compatibility

Missing content, conflicting evidence or an unrelated citation prevents unsupported conclusion. Provider agreement is not independent observation. Keep report/observation lineage through copied notes, adviser claims and summaries. Budget failures must preserve uncertainty, not replace source content with a fluent guess.

## Delivery slices and verification gates

1. Define claim/support/assumption assessments and independent versus proposed checks.
2. Integrate before intention adoption and after real outcome review through existing memory lineage.
3. Verify misleading citations, contradictory evidence, consequence gaps and observed revision; do not use JSON validity as oracle.

Acceptance is defined by PY-01 onward and the PY-C scenarios in document 02. When execution is authorized, start with meaningful focused checks, then isolated persistence/integration checks where needed, then actual provider/portal observation for semantic behavior. Catalog-only checks should inspect authoritative data and representative classifications. Never claim a runtime outcome from this source review.

No application source, dependency, migration or running service is changed by this documentation. Keep historical records, private configuration and applied migration checksums intact.
